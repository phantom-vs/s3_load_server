# Дашборд нагрузки на d-gigachat-vision-1

Локальный веб-сервер: читает access-логи бакета из `d-gigachat-logs01`,
держит в памяти скользящее окно и показывает, **откуда и куда** идёт нагрузка.
Только стандартная библиотека Python, внешних зависимостей нет.

## Запуск

```bash
cd /home/jovyan/vspyatochkin/s3_load_server
./run.sh                      # http://127.0.0.1:8765
```

Логи качаются в подкаталог **`tmp/` рядом со скриптами**, а не в системный
`/tmp`: один час логов под полной нагрузкой это 5–7 ГБ, и на многих машинах
`/tmp` столько не держит. Переопределяется переменной `S3LOAD_TMP`:

```bash
S3LOAD_TMP=/data/tmp ./run.sh
```

Каталог часа удаляется сразу после разбора — на диске в любой момент лежит не
больше одного часа логов. Если прошлый запуск убили на середине, остатки
подчищаются при старте. Текущий путь виден в `/healthz`.

Переменные окружения: `PORT`, `HOST`, `INTERVAL` (период опроса, с),
`WINDOW` (глубина окна, мин), `BOOTSTRAP` (сколько минут истории поднять
на старте), `WORKERS`.

Квота полосы задаётся флагами `server.py`:

```bash
python server.py --limit-mibs 640              # квота на каждое направление
python server.py --limit-mibs 640 --limit-combined  # квота общая на оба
```

В фоне, с логом:

```bash
nohup ./run.sh > server.log 2>&1 &
```

Открыть с другой машины — либо туннель (безопаснее):

```bash
ssh -N -L 8765:127.0.0.1:8765 <этот-хост>
```

либо слушать на всех адресах: `HOST=0.0.0.0 ./run.sh`.

Остановить: `kill $(pgrep -f "python server.py")`.

## Выбор периода

Кроме живого режима можно разобрать любой прошедший интервал: поля **Период (UTC)**
вверху страницы либо кнопки «последний час / 3 часа / 6 часов». Сервер докачает
логи за нужные часы, разберёт их и покажет тот же набор графиков и таблиц —
как снимок. Кнопка «Живой режим» возвращает к текущей нагрузке.

Обрабатывается по одному часу доставки за раз, скачанное сразу удаляется,
так что на диске в любой момент лежит не больше одного часа логов.
Предел длины периода — `--max-range` (по умолчанию 360 минут); разбор
двухчасового окна под полной нагрузкой занимает около минуты.

Через API:

```bash
curl "http://127.0.0.1:8765/api/range?from=2026-09-03%2023:22&to=2026-09-04%2001:16"
curl "http://127.0.0.1:8765/api/range/status"
```

## Что показывает

- **Баннер состояния** — норма / полоса на потолке / канал насыщен и запросы
  стоят в очереди, с указанием, какой поток занимает канал.
- **Плитки** — суммарно Гбит/с, чтение, запись, rps, задержка p50/p90, доля 404.
- **График полосы** — чтение и запись по минутам, с линией полки.
- **График задержки** — p50 и p90 по минутам, с порогом тревоги 200 мс.
- **Таблицы** — подсеть → префикс отдельно для чтения и записи, подсети,
  узлы с наибольшей полосой, префиксы с запросами впустую (404).

## Endpoints

| | |
|---|---|
| `/` | дашборд, сам обновляется раз в 20 с |
| `/api/state` | всё то же в JSON |
| `/api/range?from=&to=` | запустить разбор периода (время UTC, `ГГГГ-ММ-ДД ЧЧ:ММ`) |
| `/api/range/status` | ход разбора и результат |
| `/healthz` | состояние сборщика, 503 если данных ещё нет |

## Как это устроено

`collector.py` раз в `INTERVAL` секунд листит объекты журнала за текущий и
предыдущий час доставки, докачивает только новые, разбирает их параллельно и
подмешивает в счётчики; минуты старше окна выбрасываются. Скачанные файлы
удаляются сразу после разбора, на диске ничего не копится.

Внешних зависимостей нет: разбор строк и все расчёты — в `logparse.py`
внутри этого каталога. Наружу вызывается только `rclone`, который ищется
в `$RCLONE`, затем в `PATH`, затем в типовых местах установки; конфиг —
в `$RCLONE_CONFIG`, затем `~/.config/rclone/rclone.conf`, а если ничего нет,
флаг `--config` не передаётся и rclone берёт свой по умолчанию. Адрес
источника переопределяется через `$S3LOAD_REMOTE`. Каталог можно скопировать
на любую машину как есть.

## Важные оговорки

- **Время везде UTC.** Часы машины идут в MSK, то есть на три часа вперёд.
- **Квота задаётся в MiB/с** (`--limit-mibs`, по умолчанию 640) и намеренно
  не выводится из данных: при спокойной нагрузке максимум в окне равен
  текущей нагрузке, и любой ровный график читался бы как насыщение.
  640 MiB/с — это ровно 5·2³⁰ бит/с, то есть «5 Гбит/с» в двоичных единицах;
  в десятичных то же самое равно 5.37 Гбит/с. Единицы заданы в MiB/с именно
  чтобы эта двусмысленность не возникала.
- **Ночью 03–04.09.2026 чтение держалось на 636–643 MiB/с**, то есть ровно на
  этой отметке. Но 03.09 утром оно сутками шло на 681 MiB/с (+6.4%), а
  03.09 в 12:00–12:11 чтение 600 и запись 618 MiB/с давали вместе 1218 —
  каждое направление под квотой, сумма вдвое выше. Поэтому по умолчанию
  квота применяется к направлениям по отдельности; если у платформы иначе,
  добавьте `--limit-combined`.
- **Задержка меряется по логарифмическим бакетам** с шагом 2^(1/4), то есть
  с точностью около 19%. Для порогов этого достаточно, но точные перцентили
  так не получить.
- **Полоса записи считается по `object_size` завершённых PUT**, поэтому по
  минутам скачет: объём многочастичной загрузки приписывается минуте
  завершения. Достоверна средняя за окно.
- **Последняя минута всегда неполная** и отбрасывается автоматически.
- **Атрибуция только по `remote_ip` и префиксу.** Учётные данные общие у всех,
  поле `requester` одинаково и для определения пользователя непригодно.
- Первый цикл поднимает `BOOTSTRAP` минут истории и под нагрузкой может
  скачать несколько гигабайт — это разово.
- **Дашборд сам качает логи постоянно.** Чтобы видеть нагрузку, приходится
  читать журнал, а он под полной нагрузкой растёт на ~90 GiB в сутки, то есть
  около **4 GiB в час трафика** на сам мониторинг. В простое — единицы мегабайт.
  Если это дорого, увеличивай `INTERVAL` (объём тот же, но реже) или держи
  сервер поднятым только на время разбора инцидента.
